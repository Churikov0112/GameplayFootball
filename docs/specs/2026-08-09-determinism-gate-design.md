# Ворота №1: детерминизм симуляции + регрессионный эталон

Дата: 2026-08-09. Тип: spec (дизайн-документ). Статус: утверждён в брейншторме,
готов к плану реализации. Неизменяемый снимок — правки вести в вики.

## Контекст и цель

Дорожная карта развития игры (LAN-мультиплеер, карьеры, мобильные, уличный футбол,
катсцены, физика сетки) упирается в общий блокер: **симуляция матча привязана к
реальному времени, а тестов нет**. Любая будущая правка рискует молча сломать
текущий геймплей, который критически важно сохранить 1-в-1.

Этот документ — первое ворота: сделать симуляцию детерминированной и получить
регрессионный эталон, который машинно проверяет «геймплей не изменился».

**Жёсткое ограничение:** никакие изменения геймплея. В `gamedefines.hpp` не
меняется ни одна константа, логика `Match::Process` не переписывается.

## Источник переноса

Репозиторий google-research/football (GRF) — форк того же движка Blunted2.
Ветка `origin/google-brain` нашего репозитория идентична GRF v2.10.1
(проверено по 8 ключевым файлам: `match.cpp`, `gametask.cpp`, `main.cpp`,
`gamedefines.hpp` и др. — побайтово совпадают с клоном).

GRF уже решает эти ворота: отвязка времени (`BumpActualTime_ms`), сид
(`randomize(seed)`), сериализация состояния (`EnvState`/`ProcessState`),
headless-шаг (`GameEnv::step`). Переносим **только совпадающие куски** —
GRF менял геймплей (проверено оценкой пользователя и по коду), его игровую
логику в master не тащим.

### Что отличает GRF от нашего master (подтверждено)

- GRF расходится с master на 410 файлов, 20 839 добавлений / 38 971 удаление.
- GRF выбросил: физику ODE, аудио, меню/лигу (52 файла), БД, HID, Scheduler.
- GRF переписал геймплей: `humanoid` (1932 строки правок), `elizacontroller`
  (749), `teamAIcontroller` (1019), `team` (693), `humancontroller` (252).
- При этом **структура данных сохранена**: поля классов в основном совпадают
  с master (Match 16/21, Ball 8/9, Player 15/16). Менялась логика, не данные.

## Дизайн

### Секция 1. Отвязка времени (`Match::Process`)

- В `src/onthepitch/match.cpp` убрать чтение
  `EnvironmentManager::GetInstance().GetTime_ms()` в `Process()` (строки ~853-855):
  `timeSincePreviousProcess_ms` и `previousProcessTime_ms` нигде не используются
  в расчётах — только присваиваются. Проверено по коду.
- Время продвигается самим матчем: `actualTime_ms += 10` уже есть (`match.cpp:964`),
  `matchTime_ms += 10 * (1.0f / matchDurationFactor)` тоже (`:963`).
  Фиксированный шаг 10 мс на один вызов `Process()`.
- Добавить `Match::BumpActualTime_ms(unsigned long)` по образцу GRF (`match.hpp`).
  В нашем master `Process()` сам делает `+= 10` — метод нужен для симметрии и
  внешнего управления временем в будущем (реплеи/паузы).
- `GetMatchTime_ms()`/`GetActualTime_ms()` остаются источниками времени.

Происхождение шага 10 мс: `physics_frametime_ms` = 10 (дефолт, `main.cpp:288`,
документирован в `docs/wiki/константы.md`) + жёсткий `+= 10` в `match.cpp`.
Это две независимые десятки; связывать их — изменение геймплея, вне scope.

Критерий: игра компилируется и играется так же; в Process-фазе не читается
глобальный `time_ms`.

### Секция 2. `EnvState` + `ProcessState` (ядро)

Переносим механизм сериализации из google-brain, ограниченный полями,
существующими в нашем master.

**2a. `EnvState`** (`src/defines.hpp`/`.cpp`): raw-memcpy сериализатор —
`process(T&)` (запись/чтение через `memcpy`), `process(std::vector<T>&)`,
`process(std::list<T>&)`, `process(Player*&)`, `process(Team*&)`.
У нас нет `GameEnv`/`GameContext`/`AIControlledKeyboard` — `EnvState` держит
только строку состояния, позицию, флаги `load/failure/validate`.
Части для `AIControlledKeyboard`/`SetControllers`/`SetAnimations` пропускаем.

**2b. `ProcessState` в игровых классах** — только совпадающие поля,
с переименованиями:

| Класс | Файл | Поля | Правки |
|---|---|---|---|
| `Match` | `match.cpp` | 16 полей | `lastGoalTeam`→`lastGoalTeamID`, `bestPossessionTeam`→`bestPossessionTeamID`; нет `first_team`/`second_team` |
| `Ball` | `ball.cpp` | 8 полей | нет `valid_predictions` |
| `Player` | `player.cpp` | 15 полей | нет `manMarking` (в master это `GetManMarkingID()` в контроллере) |
| `PlayerBase` | `playerbase.cpp` | `ProcessStateBase` | **без** `humanoid->ProcessState` и `controller->ProcessState` — они ведут в переписанный AI |

**Сознательно исключено (отложено):** `ProcessState` для `Team`, `Referee`,
`Officials`, `MentalImage`; сериализация `humanoid`/`controller`. Причины:
- humanoid — анимация, не влияет на детерминизм симуляции;
- controller/teamAIcontroller — переписанный AI, решения которого уже
  отражаются в позициях игроков;
- `mainSelectedPlayer` (автопилот GRF) в master отсутствует.

**2c. Обёртка сравнения:** `std::string CaptureMatchState(Match*)` — создаёт
`EnvState`, прогоняет `match->ProcessState()`, возвращает строку. Для хранения
сравниваем SHA-256, не сырые мегабайты.

Критерий: компиляция; два прогона с одним сидом дают одинаковый хэш.

### Секция 3. Сид

- Добавить `randomize(unsigned int seed)` по образцу GRF:
  `srand(seed); rand(); randomseed(seed);` (boost RNG).
  В master уже есть `randomseed()` без аргумента (`main.cpp:283-284`) —
  добавляем перегрузку с параметром.
- Один фиксированный сид по умолчанию: 42 (как в GRF). Параметр раннера
  `--seed` не вводим.
- `ScenarioConfig` НЕ переносим в этой версии: стартовое состояние — из
  стандартных `MatchData` БД, как в обычной игре. Параметризация старта —
  задел на будущее (уличный футбол).

Критерий: одинаковый сид → одинаковый хэш; разные сиды → разные хэши (обычно).

### Секция 4. Headless-раннер и эталон

- Отдельный бинарник в `tools/` (например `tools/determinism/`), НЕ трогая
  `gameplayfootball`. Отдельный CMake-таргет.
- **Общая инициализация выносится в общий код** (используется и игрой, и
  раннером), чтобы избежать дрейфа между путями: `Database.Load`,
  `MatchData` из БД, создание `Match`. Раннер не дублирует инициализацию
  вручную — он вызывает те же функции, что и игра.
- Раннер работает без GUI и без звука: не создаёт `SystemManager` с
  `GraphicsSystem`/`AudioSystem`, не открывает окно. Только данные +
  симуляция.
- Раннер создаёт `Match` напрямую (без `GameTask`, без рендера, без
  Scheduler), без HID-устройств (боты `ElizaController` не требуют HID).
- Цикл: `randomize(42)` один раз, затем N вызовов `Process()` (N — параметр,
  дефолт 5000 = 50 секунд симуляции). `Get()`/`Put()`/`PreparePutBuffers` не
  вызываются.
- Два режима:
  - `run` — прогнать, напечатать SHA-256 хэш;
  - `check <expected_hash>` — сравнить с эталоном, код выхода 0 (совпало) /
    1 (расхождение) — для CI.
- Эталон закоммичен рядом с раннером: `tools/determinism/reference.txt`.

*Открытый момент для реализации:* не требует ли `Match::Process` минимального
цикла буферов (например `GetIterations() < 2` в `Put()`); при необходимости
раннер имитирует минимальный цикл. А также: какие именно части
инициализации `main.cpp` реально нужны `Match`'у (возможно, часть
менеджеров ресурсов окажется лишней) — выясняется при реализации.

Критерий: `run` и `check <тот же хэш>` — успех; два прогона — одинаковый хэш.

## Инварианты (что проверяем в итоге)

1. Геймплей не тронут: в master не меняется ни одна константа
   `gamedefines.hpp`, не переписывается логика `Process` — только отвязка
   времени (мёртвый код) + добавленные методы сериализации/сида.
2. Один сид → один хэш. Разные сиды → разные хэши.
3. `check` возвращает 0 при совпадении, 1 при расхождении.
4. Обычная игра (`gameplayfootball`) запускается и играется без изменений.

## Отложено (не переносится сейчас)

- `ProcessState` для `Team`/`Referee`/`Officials`/`MentalImage`.
- Поля `manMarking`, `valid_predictions`, `first_team`/`second_team`.
- Сериализация `humanoid`/`controller`.
- `ScenarioConfig` (параметризация стартового состояния).
- Связывание жёсткой десятки `match.cpp:963` с `physics_frametime_ms`.
